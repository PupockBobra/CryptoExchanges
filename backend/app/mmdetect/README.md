# Оценка присутствия маркет-мейкеров в стаканах СПБ Биржи

Отвечает на вопрос: **на какой объём и с каким спредом стоят маркет-мейкеры**
в стаканах вечных фьючерсов СПБ Биржи.

Прямой идентификации ММ в анонимном стакане нет. Оценка строится на двух
признаках, которые есть у обязанного котировщика и нет у случайного потока:
**устойчивость** (заявка одного и того же РАЗМЕРА держится в стакане снимок за
снимком) и **двусторонность** (заявка такого же размера стоит с противоположной
стороны).

⚠️ Удаление от мида при этом **не обязано совпадать** у двух котировок: обязательство
ММ связывает их объёмы, а не расстояния. Удаление — это выход метода, а не условие;
оно показывается отдельно по каждой стороне.

Вкладка в приложении: **SPB → MM Presence**.

---

## Как собираются данные

Коллектор `app/mmdetect/collector.py` запускается из lifespan `main.py`
(`_spawn(mmdetect_collector_loop())`) и работает сам, без участия страницы:

- 15 инструментов (`MMD_BASES` в `config.py`), Finam MIC `RUSX`;
- **gRPC-стрим** держит книгу в памяти, таймер снимает копию **раз в 5 с** по
  epoch-выровненной сетке; REST-поллинг — фолбэк, если SDK нет или канал упал
  (полный обход 15 тикеров ~8 с, то есть 5-секундная сетка по REST недостижима —
  ради этого и стрим);
- сохраняются **20 ближних уровней на сторону** в `ob_snapshot_level`
  (`ts, symbol, side, level_idx, price, volume`);
- только в торговые часы СПБ (`_is_trading_now` из `spb/spread_etl.py`).

**Историю нельзя бэкфилить**: Finam отдаёт только живой стакан. Данные копятся с
момента первого запуска, задним числом — никак.

Дисциплина, без которой метрика была бы неверной, а не просто неточной:

- **Замерший фид не должен выглядеть как стоящая котировка.** Персистентность —
  это буквально «объём не менялся», поэтому мёртвый стрим дал бы идеальную 1.0.
  Точка сетки пишется, только пока сессия жива И книга инструмента обновлялась
  не позже `STALE_AFTER_SEC`; иначе точка считается пропуском.
- **Пропуски считаются, а не игнорируются.** Их доля пишется в
  `ob_capture_session` и показывается рядом с каждой оценкой: персистентность
  0.9 на окне, где потеряна треть снимков, — не то же самое, что на полном.
- `retries=2` на REST: одиночная попытка отдаёт ложные 404 (наблюдалось на
  COHR/COIN/UBER), а фантомный пропуск смещает метрику присутствия.

### Объём на диске

Замерено на реальном сборе: **~143 строки/с ≈ 8.8 млн строк и ~1.2 ГБ за
торговый день**, сжатие **7.1×**.

Поэтому: чанк **6 часов** (при недельном чанке по умолчанию политика сжатия не
срабатывает почти неделю — она ждёт, пока весь диапазон чанка станет старше
порога), сжатие через **12 часов**, ретеншен **14 дней**. Установившийся размер
≈ 3 ГБ.

### Ручной прогон

```bash
docker compose up -d timescaledb redis
cd backend
GRPC_DNS_RESOLVER=native .venv/bin/python - <<'PY'
import asyncio, os
os.environ["DATABASE_URL"] = "postgresql://arbi:arbi@localhost:5432/arbidb"
from app.db.timescale import init_db
from app.mmdetect.collector import mmdetect_collector_loop
async def main():
    await init_db()
    await asyncio.wait_for(mmdetect_collector_loop(), 600)   # 10 минут
asyncio.run(main())
PY
```

⚠️ `GRPC_DNS_RESOLVER=native` нужен **только на macOS**: встроенный в grpc
c-ares резолвер здесь не резолвит `api.finam.ru` (`DNS timeout`). В Docker и на
проде не требуется.

## Как запустить страницу

Отдельного запуска нет — вкладка входит в обычную сборку:

```bash
docker compose up --build          # локально
```

Страница: **SPB → MM Presence**. Все пересчёты идут на бэкенде по стору снимков,
к Finam страница не ходит вовсе — поэтому пороги можно крутить сколько угодно, и
анализ работает на машине без доступа к рынку.

Эндпоинты (`/api/mmdetect`):

| Метод | Что |
|---|---|
| `GET /instruments?hours=` | покрытие сбора по каждому инструменту |
| `GET /analyze?ticker=&hours=&mode=&persistence_min=&volume_tol=&symmetry_tol=&bin_steps=` | полная оценка + heatmap + серии |
| `GET /summary?...` | та же оценка одной строкой на инструмент |
| `GET /export.csv?...` | сводка + подтверждённые кластеры |

## Как читать метрики

### Объём ММ и несколько котировщиков

В одном стакане может стоять **несколько ММ** — на AMD видно как минимум двух.
Поэтому детектор ищет не один размер, а все устойчивые размеры на каждой стороне,
и сводит их в пары по совпадению объёма. Каждая пара — отдельный котировщик со
своим объёмом, своими удалениями и **своим спредом**; на графике у каждого своя
линия, в таблице «Обнаруженные котировщики» — своя строка.

В карточке сверху показаны:
- **объём всего** — сумма `min(V_bid, V_ask)` по всем подтверждённым парам;
- **крупнейший** — самая большая пара;
- **спред крупнейшего** — потому что усреднять спреды разных участников бессмысленно.

⚠️ Разделение идёт **по размеру заявки**: два ММ, стоящие одинаковым объёмом,
сольются в одного, а один ММ, выставляющий две заявки разного размера, будет
посчитан как двое.

### Заявка внутри чужого уровня (кратность)

Уровень стакана показывает **сумму всех заявок по этой цене**, поэтому заявка ММ
исчезает в большем числе, как только рядом встаёт такая же чужая. Замер на UBER
(2127 снимков): уровень bid показывал 350 в 51.8% снимков и 700 в 48.0% —
**никогда одновременно, вместе 99.8%**. То есть одна заявка на 350, которая не
уходила, и вторая такая же, приходившая на ту же цену половину времени. Поиск
точного размера давал 0.52, и ММ не подтверждался.

Поэтому уровень засчитывается кандидату V, если он несёт **целое число** V — до
3× (`MAX_STACK_MULTIPLE`). Допуск меряется относительно V, а не k·V, так что
стопка должна быть точной кратностью, а не просто большим числом. Колонка
**«один на уровне»** в таблице котировщиков показывает, как часто заявка стояла
на своей цене одна.

⚠️ Обратная сторона правила: кандидат, который **никогда** не стоял один, — это
вывод из чужих заявок, а не наблюдение. Такие отсекаются (`MIN_ALONE_SHARE` =
10% засчитанных снимков): сразу после включения кратности на AMD появились
«котировщики» на 17 и 5 лотов с долей «один на уровне» 1–2%.

`не подтверждён` означает не «ММ нет», а «одинаковых по размеру кластеров с двух
сторон выше порогов не нашлось». Опустите порог персистентности и посмотрите.

### Спред ММ vs наблюдаемый

Показаны **оба, рядом, намеренно**. Наблюдаемый — по лучшим котировкам; в них
вклинивается клиентский поток и занижает то, что видно. Спред котировщика
считается по ценам его собственных заявок с двух сторон, снимок за снимком.

⚠️ Если котировщик стоит глубоко в стакане, его спред будет заметно больше
наблюдаемого. Это не ошибка: рядом с числом указано удаление каждой стороны.

### Удаление — в шагах цены, и это ВЫХОД, а не условие

Цена плывёт, котировщик переставляет заявку вместе с рынком, поэтому удаление
меряется от середины стакана в шагах цены, а не в абсолютной цене.

Но само удаление **не участвует в поиске**. Первая версия детектора требовала,
чтобы обе котировки стояли на одинаковом удалении, — и слепла. Замер на AMD
(1433 снимка, 6 ч): заявка ~140 лотов присутствовала на ask в 96.4% снимков, на
bid в 99.4%, одновременно с двух сторон в 96.0%, а её удаление гуляло (34% на
0–30 шагах, 38% на 30–60, 22% на 150–180). Персистентность «по месту» не
поднималась выше 0.50, и ММ не подтверждался никогда. Причина проста: клиентские
заявки на 1–20 лотов встают перед ММ, тянут середину стакана к себе, и удаления
двух его котировок расходятся, хотя сам он ничего не двигал.

Сейчас единственное, что делает расстояние, — ограничивает зону поиска
(**радиус**, по умолчанию 0.5% от цены), чтобы в оценку не попал глубокий чужой
объём. Ширина бина осталась только для heatmap.

### Двусторонняя глубина в коридорах

Кумулятивный объём внутри ±0.1 / 0.25 / 0.5% от мида, `min(bid, ask)`.
Колонка **«книга обрезана»** — доля снимков, где сохранённая глубина кончилась
внутри коридора: там число является **нижней оценкой**, а не «дальше пусто».

### Пропуски

`Пропуск` — доля точек 5-секундной сетки в торговых часах, для которых снимка
нет (сборщик не работал, фид молчал, книга была пуста). Персистентность считается
по снятым снимкам, поэтому большой пропуск обесценивает любую долю рядом.

### Что метод не может

- Даёт **верхнюю оценку**: алго-участники, не являющиеся ММ, котируют так же.
- Несколько ММ по одному инструменту не разделяются — это сумма.
- Айсберги видны только надводной частью.
- ММ обычно котирует с запасом к обязательству, поэтому оценка ≠ обязательство.

Ровно это написано и на самой странице — сверху, а не мелким шрифтом внизу.

## Разработка

Ядро (`core.py`) не знает ни про API, ни про БД, ни про Finam, и покрыто
синтетическими стаканами (`tests/test_mmdetect_core.py`, 20 тестов):

1. идеальный ММ с фиксированным объёмом и спредом при плывущей цене — детектор
   обязан его найти;
2. чистый случайный поток — не должен найти ничего;
3. односторонняя стенка — должна быть отсечена фильтром симметрии (и отдельный
   тест доказывает, что отсекает именно фильтр, а не нехватка данных);
4. котировщик, чьи две заявки стоят на РАЗНОМ удалении (клиент вклинился с одной
   стороны и утащил мид) — должен находиться;
5. два ММ одновременно — должны быть показаны как двое, с разными объёмами и
   разными спредами, а не усреднены в одного.

```bash
cd backend && .venv/bin/pytest tests/test_mmdetect_core.py -q
```

Все пороги — в `config.py` (`DetectParams`), ни один не зашит в алгоритм;
страница передаёт их в каждом запросе.
